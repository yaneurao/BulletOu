# NNUE K-A2 Training

<a href="../../ja/shogi/ka2.md"><img alt="日本語で読む" src="https://img.shields.io/badge/Lang-日本語-DC2626?style=flat-square"></a>

[Back to Reference index](../README.md)

`--eval-type NNUE_KA2` trains a YaneuraOu NNUE whose input is `FeatureSet<Features::K, Features::A2>` (architecture file `source/eval/nnue/architectures/ka2_*.h`, auto-generated by `nnue_arch_gen.py`). The network is the same 4-layer ClippedReLU as [HalfKP](halfkp.md) and [K-P](kp.md); only the input feature differs.

The closely-related `--eval-type SFNN_KA2` trains the same input feature with the SFNN-1536 architecture (LayerStacks=9, see [§4.4](../tutorial/4-train.md) and [SFNN-1536](sfnn-1536.md)).

## Architecture

L1 / L2 / L3 sizes are selected via `--arch NNUE_ka2_<L1>x2_<L2>_<L3>`. The default is `NNUE_ka2_256x2_32_32` matching the K-P network shape, but free-form is meant to be exploited here — for example `--arch NNUE_ka2_256x2_64_64` doubles the post-FT hidden capacity to make up for KA2's lack of king-anchor cross product (compared to HalfKA). Below shows the default:

```
Shogi position
        │
        │  K + A2 sparse input (1,791 dims per perspective)
        ▼
   L0 affine + ClippedReLU                ← shared between own / opponent perspectives
        ▼
   accumulator (256 dims × 2 perspectives = 512 dims concatenated)
        │
        │  L1 affine (512 → 32) + ClippedReLU
        ▼
        │  L2 affine (32 → 32) + ClippedReLU
        ▼
        │  Out affine (32 → 1)
        ▼
      eval (centipawn-ish scalar)
```

## Input features

`FeatureSet<K, A2>` composes two YaneuraOu feature sets:

| Sub-feature | Dim | Max active | Hash | Meaning |
|---|---|---|---|---|
| **K** (`features/k.h`) | 162 (= 81 × 2) | 2 | `0xD3CEE169` | Own king at one of 81 squares + opp king at one of 81 squares |
| **A2** (`features/a2.h`) | 1629 (= `e_king`) | 40 | `0xA20DCB9B` | All pieces (kings included) as BonaPiece values, with the enemy king collapsed onto the friend king plane (v2 encoding) |

Total per perspective: **1791 dims**, max **42** active features (2 from K + 40 from A2). The two physical kings each fire **twice per perspective**: once in the K region (as a king) and once in the A2 region (as one of the 40 pieces, after v2 collapse). This double-firing is the intended semantics of `FeatureSet<K, A2>`.

`FeatureSet<Head, Tail>` (`feature_set.h`) places Tail indices first and shifts Head indices by `Tail::kDimensions`, so:

- Indices `0 .. 1547` are A2 non-king BonaPiece values (same layout as P).
- Indices `1548 .. 1628` are A2 king plane (both kings collapse here via v2 encoding).
- Indices `1629 .. 1709` are K-own-king features (own king at square 0..80, perspective-rotated).
- Indices `1710 .. 1790` are K-opp-king features (opp king at square 0..80, perspective-rotated).

The combined feature hash, used in the `nn.bin` header:
```
FeatureSet<K, A2>::kHashValue
  = K::kHashValue ^ (A2::kHashValue << 1) ^ (A2::kHashValue >> 31)
  = 0xD3CEE169 ^ 0x441B9736 ^ 0x00000001
  = 0x97D5765E
```

## Difference vs. K-P and HalfKA

| | K-P | **K-A2** | HalfKA_hm2 |
|---|---|---|---|
| Input dim / perspective | 1,710 | **1,791** | 73,305 |
| Max active | 40 | **42** | 40 |
| Both kings represented as a piece feature? | No (P excludes kings) | **Yes** (A2 includes both kings, v2 collapsed) | Yes |
| King × piece cross product in feature? | No | **No** | Yes (HalfKA bakes it in) |

K-A2 sits between K-P and HalfKA_hm2 in expressiveness: it lets the network see both kings inside the piece feature itself (which K-P does not), but it still does not encode king × piece interactions in the input layer the way HalfKA does. Practically, expect loss curves comparable to K-P — slightly better with the same `--arch`, much weaker than HalfKP / HalfKA at small `--arch`.

## Actual usage

### Command

Standard 4-layer NNUE network (default `--arch NNUE_ka2_256x2_32_32`):

```bash
./target/release/examples/bulletou \
    --eval-type NNUE_KA2 \
    --teacher teachers/ \
    --output checkpoints/my-ka2
```

Wider hidden layers (256x2 FT, 64-dim hidden):

```bash
./target/release/examples/bulletou \
    --eval-type NNUE_KA2 \
    --arch NNUE_ka2_256x2_64_64 \
    --teacher teachers/
```

SFNN-1536 architecture with KA2 input:

```bash
./target/release/examples/bulletou \
    --eval-type SFNN_KA2 \
    --arch SFNN_ka2_1536_15_32_k3k3 \
    --teacher teachers/
```

Everything else (training schedule flags, save layout, resume from `state.bin`, top-level `summary-learn.log`) is identical to [HalfKP](halfkp.md) — only `--eval-type` (and the input dim) differs.

### Save layout

```
checkpoints/my-ka2/
├── summary-learn.log
├── 0001/
│   ├── nn.bin                         ← YaneuraOu / Stockfish (nnue-pytorch) compatible NNUE binary
│   ├── state.bin                      ← resume data (weights + Ranger optimizer state)
│   └── learn.log
├── 0002/
├── ...
└── 000N/
    ├── nn.bin
    ├── state.bin
    └── learn.log
```

### `nn.bin` format

Same binary layout as [HalfKP's `nn.bin`](halfkp.md#nnbin-format); the only differences are:

- Header `network_hash` and `feature_transformer_hash` differ (they include `FEATURE_HASH_KA2 = 0x97D5765E`).
- Header `description` string starts `Features=K-A2(Friend)[1791->256x2],...`.
- L0 size: `1791 × L1` (i16) instead of `125388 × L1` (HalfKP) or `1710 × L1` (K-P).

L1 / L2 / Output layers are byte-identical between HalfKP / K-P / K-A2 for the same `--arch` (same sizes, same i8 row-major SIMD-padded layout).

### Loading in YaneuraOu

The trained `nn.bin` requires a YaneuraOu build whose architecture header matches your `--arch` triple. Build by passing the matching edition name:

```bash
# For NNUE_KA2 --arch NNUE_ka2_256x2_32_32 (default)
make normal YANEURAOU_EDITION=YANEURAOU_ENGINE_NNUE_ka2_256x2_32_32

# For NNUE_KA2 --arch NNUE_ka2_256x2_64_64
make normal YANEURAOU_EDITION=YANEURAOU_ENGINE_NNUE_ka2_256x2_64_64

# For SFNN_KA2 --arch SFNN_ka2_1536_15_32_k3k3
make normal YANEURAOU_EDITION=YANEURAOU_ENGINE_SFNN_ka2_1536_15_32_k3k3
```

YaneuraOu's `Makefile` auto-runs `nnue_arch_gen.py` for unknown editions, so the matching architecture header is generated on the fly. Use **underscores** (not hyphens) in the dimension part of the edition name to avoid a `clang -Wc99-extensions` warning. See [§8 Engine](../tutorial/8-engine.md) for the load procedure.

### Common CLI flags

| Flag | Meaning | Default |
|---|---|---|
| `--eval-type` | `NNUE_KA2` (4-layer) or `SFNN_KA2` (LayerStacks-1536) | (required) |
| `--arch` | `NNUE_ka2_<L1>x2_<L2>_<L3>` (`L1` must be a multiple of 32) | `NNUE_ka2_256x2_32_32` |
| `--teacher` | Teacher file / directory / comma-separated list | (required) |
| `--output` | Checkpoint parent directory | `checkpoints/<eval-type>-<arch>` (e.g. `checkpoints/NNUE_KA2-NNUE_ka2_256x2_32_32`) |

See [HalfKP Training](halfkp.md) for the full flag list (training schedule / save / resume / log flags are identical across the NNUE family).
