# FP32 checkpointから16bit重みのnn16.binを書き出す

`export-nn16` は保存済みの `state.bin` から **L1・L2・L3の重みをint16** に量子化します。
FTのint16形式は変更しません。再学習は不要です。従来の `nn.bin`、通常学習、QAT、学習中のqvalidは変更しません。
8bitの `nn.bin` から精度は復元できないため、入力には同じcheckpointのFP32 `state.bin` が必要です。

これは **BulletOu独自の実験形式** です。従来のやねうら王では読めません。対応するreaderと整数演算が必要です。
やねうら王の実装自体はこの変更には含めません。

## 書き出しコマンド

```powershell
$checkpoint = "D:\BulletOu-snapshots\学習フォルダ\0023"
.\target\release\examples\bulletou.exe export-nn16 `
  --arch SFNN_halfka2_1024_8_64_progress8 `
  --state-bin "$checkpoint\state.bin" `
  --weight-scale 4096 `
  --output "$checkpoint\nn16.bin"
```

- `--arch`: checkpointと同じarch。SFNNのみ対応。
- `--state-bin`: FP32重みの保存ファイル。optimizerは読み込まず、GPUも使用しません。
- `--settings-file`: 保存時の `bulletou-settings.json`。省略すると `state.bin` と同じフォルダから読みます。見つからなければエラーになります。
- `--weight-scale`: L1/L2/L3共通の量子化倍率QB。デフォルト4096。64～16384の2のべき乗を指定できます。
- `--output`: 出力ファイル。省略するとカレントフォルダの `nn16.bin`。既存ファイルは上書きしません。

FT/shared/axis/pairとcount gateは既存のnn.binと同じfold処理を使います。
FT/sharedの係数がstateに記録されていれば、その値を優先します。axis/pair/count設定は保存時のJSONとcount.binを使います。
したがって新しい学習用に変更したJSONを指定しないでください。count.binが必要な場合も元の集計ファイルが必要です。
再開時のrebase、factorizer追加、optimizer更新は行いません。

progress付きarchではcheckpointの分類器を同じ出力フォルダの `progress.bin` に書き出します。
既存の同名ファイルと内容が一致すれば変更せず使い、異なればエラーにします。progressはnn16.binに埋め込みません。
`nn16.bin` は一時ファイルへの書き出し完了後に公開します（同一ボリュームのハードリンクを使用。NTFS等が必要です）。

## 倍率と丸め

| 項目 | 従来のnn.bin | nn16.binのデフォルト |
|---|---|---|
| FT weight / bias | int16、倍率127 | 同じ |
| L1/L2/L3 weight | int8、倍率64 | int16、倍率4096 |
| L1/L2/L3 bias | int32、倍率8128 | int32、倍率520192 |
| FC重みの刻み幅 | 1/64 | 1/4096（64倍細かい） |
| FC重みの表現範囲 | -2～1.984375 | -8～7.999755859375 |

```text
QA = 127
QB = 4096
weight_integer = round(weight_fp32 * QB)
bias_integer   = round(bias_fp32 * QA * QB)
```

最近傍丸めで、ちょうど中間ならゼロから遠い側です。FC weightがint16、biasがint32に収まらない場合、
黙ってclampせずエラーにします。QBを下げるか、重みを見直してください。FTは従来と同じ丸め・int16へのclampです。
QATで学習したstateも書き出せますが、学習時に模擬したのは倍率64のL1なので、16bit化による改善は保証されません。

## やねうら王側向けバイナリ仕様

整数はすべてlittle-endian。`pad32(n) = (n + 31) / 32 * 32`（整数除算）。
通常のSFNNの並びを保ち、ヘッダのversion変更、QB追加、FC重みの要素サイズ変更を行います。

```text
u32 version       = 0x7AF32F17  (従来は0x7AF32F16)
u32 model_hash    = 0x3C203B32
u32 descriptionのUTF-8バイト数
bytes description（終端NULなし）
u32 QB                        ← 新規フィールド。デフォルト4096
u32 FT_hash       = 0x5F134AB8
LEB128 block: FT bias    int16 × FT幅
LEB128 block: FT weights int16 × 入力特徴数 × FT幅

以下をbucket数回繰り返す:
  u32 network_hash = 0x6333718A
  int32 L1 bias    × L1出力数
  int16 L1 weights × L1出力数 × pad32(FT幅)
  int32 L2 bias    × L2幅
  int16 L2 weights × L2幅 × pad32(2 * H1)
  int32 L3 bias    × 1
  int16 L3 weights × pad32(L2幅)
```

LEB128 blockは既存と同じ `COMPRESSED_LEB128` の17byte、u32のpayload byte数、signed LEB128のpayloadです。
FT重みは `[feature][neuron]`、FC重みは `[out][in]` の行優先。paddingは0で、ファイルにはSIMD向け並べ替えを施しません。
L1出力数は `H1 + (skipありなら1、なしなら0)` です。
descriptionには既存の特徴名・FT幅・bucket数に加え、`;FCWeightBits=16;QB=4096;H1=8;Skip=0;H2=64` のような情報を付加します。
hash値は既存SFNNと共通ですが、versionとQBによって読み方を区別してください。

## 推論時のシフトと出力単位

FTの計算・活性値の8bit化は既存SFNNと同じです。FCの活性値まで16bitに変更するわけではありません。
`s = log2(QB)` とすると、FCの積和 `z = bias + Σ(weight * activation)` に対して:

```text
CReLU(z)    = clamp(z >> s, 0, 127)
SqrCReLU(z) = min((z*z) >> (2*s + 7), 127)
```

SqrCReLUは負のzも二乗します。QB=4096ではシフトは12と31です。L2入力は `[SqrCReLU; CReLU]`。
skipありならL1のskip出力をL3の積和に加算します。
**積和はint64などで安全に計算してください。重みの型がint16だからといってint32積和の安全性は保証されません。**
二乗はさらに広い型、または結果が飽和する範囲の先行判定でオーバーフローを防いでください。
BulletOuのCPU検証はint64積和・int128二乗を使用します。

```text
network_output ≈ raw16 / (QA * QB) = raw16 / 520192
従来のraw単位 ≈ raw16 * 64 / QB  = raw16 / 64
```

したがって、従来FV_SCALE=24の出力単位を維持するなら、QB=4096では
`engine_score = raw16 / (64 * 24) = raw16 / 1536` です。
あるいは最後にrawを64で割って従来単位に戻し、従来通りFV_SCALE=24で割ります。
**raw16をそのまま24で割ると、評価値が約64倍になるため不適切です。**
倍率を変えること自体は教師データのscaleや学習のloss targetを変えません。

## 書き出したファイルのqacc / qloss

```powershell
.\target\release\examples\bulletou.exe quantized-test `
  --arch SFNN_halfka2_1024_8_64_progress8 `
  --nn-bin "$checkpoint\nn16.bin" `
  --test-teacher C:\shogi\teacher\test\test20231010_fg2021_dls5_ryfc20_ev8250k825.hcpe `
  --mode cpu-exact `
  --wrm-in-offset 0 --wrm-target-offset 0
```

archは実際のcheckpointに合わせて指定します。
nn16は現在CPU整数検証のみ対応し、`--mode gpu` はエラーです。ファイルのヘッダを読んで倍率を取得します。
検証局面数を省略すると全局面。教師scale、WRMの各係数、lambda等は学習時と揃えてください。
学習ログと比較する値は出力の **train-scale accuracy/loss**（raw16/520192）です。
accuracyは引き分けを除いた勝敗との符号一致率、lossは指定したWRM等のlossです。
engine-scaleの表示では `--fv-scale 24` を**従来の倍率64での値**として解釈し、内部で上記の64倍補正をします。
既存のGPU近似qvalidとCPU整数検証には活性値の整数丸め等の差があるため、8bit版との比較も同じCPU経路で行ってください。
